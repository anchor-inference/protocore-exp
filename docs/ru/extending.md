# Расширение ядра

> Аудитория: инженер, добавляющий возможность в **чистое ядро** (`protocore/`)
> или подключающий за ним новый бэкенд. Область: библиотека ядра (`protocore/`).

Ядро — это набор `Protocol`-ов и неизменяемый ReAct-рантайм. Вы расширяете его
**снаружи** — реализуя контракт, регистрируя hook, переключая флаг
`LoopConstants` или внедряя секцию системного промпта — но **никогда не
редактируя цикл**. Эта страница — руководство по выбору правильной точки
расширения, за которым следуют два жёстких правила, ограничивающих любое
расширение.

Полную детализацию по каждой точке расширения в разрезе подсистем см. в
[`architecture.md`](./architecture.md) — [таблице точек
расширения](./architecture.md), [соглашениях](./architecture.md) и заметках
«Extension protocol» в каждом разделе.

## Выбор точки расширения

Существует пять точек расширения. Они не взаимозаменяемы; каждая отвечает на
свой вопрос.

| Вы хотите… | Используйте | Где |
|---|---|---|
| Предоставить конкретный бэкенд, который ядро знает лишь как интерфейс (LLM, хранилище, транспорт, память, рабочее пространство, навыки, …) | **Адаптер `Protocol`** | модуль в `contracts/`, реализованный хостом |
| Наблюдать, решать, преобразовывать или оборачивать поведение в точке прогона (вызовы инструментов, обмен с провайдером, границы сессии и уплотнения) без изменения цикла | **Регистрация на шве жизненного цикла** | `contracts/middleware.py`, диспетчер — `hooks/manager.py` |
| Включить/выключить возможность или настроить числовое/строковое значение для каждого тенанта | **Флаг `LoopConstants`** | `contracts/runtime_constants.py` |
| Добавить статический текст-руководство/персону/ориентир в системный промпт | **Секция системного промпта** | `QueryEngineConfig.system_prompt_sections` |
| Заменить одно продуктовое решение о ходе — бюджет, подталкивание, то, что заслуживает пустой ответ | **Политика хода** | `contracts/turn_policy.py`, подставляется в `QueryEngine.turn_policies` по имени |

Порядок принятия решения, от самого быстрого:

1. **Это просто значение или переключатель вкл/выкл?** → флаг RC. Без нового
   пути кода.
2. **Это статический текст, который модель должна видеть всегда?** → секция
   системного промпта.
3. **Это реакция в точке жизненного цикла (наблюдать/решать/преобразовывать/
   оборачивать/уведомлять)?** → регистрация на шве жизненного цикла.
4. **Это решение, которое принимает драйвер хода, — когда ход кончается, что
   заслуживает пустой ответ, какой потолок применяется?** → политика хода,
   подставленная по имени.
5. **Это целый новый бэкенд / возможность за интерфейсом?** → адаптер
   `Protocol` (в хосте).

Если ничего из этого не подходит, вы, вероятно, собираетесь изменить цикл —
**остановитесь** и перечитайте [жёсткие
правила](#жёсткие-правила-не-нарушайте-их).

### Реализация `Protocol` (адаптер хоста)

**Используйте, когда** ядру нужна возможность, которой оно намеренно не владеет:
обращение к LLM, сохранение прогонов/сессий/блобов, поиск, хранение памяти или
единиц рабочего пространства, диспетчеризация субагентов, транспорт вызовов
инструментов, рендеринг шаблонов промптов. Ядро объявляет *форму* как
`Protocol`; конкретная реализация живёт в хосте (или в другом
потребителе) и **внедряется** через границу.

**Единого `protocols.py` нет** — каждый интерфейс находится в собственном модуле
внутри `contracts/`. Основные интерфейсы (по одной строке на точку расширения,
полный список — в [таблице точек расширения](./architecture.md)):

| Protocol | Модуль |
|---|---|
| `ILLMProvider` / `IProviderChain` | `contracts/llm.py` |
| `RuntimeConstantsProvider` | `contracts/runtime_constants.py` |
| `ISessionStore` / `IRunStore` | `contracts/session.py` / `contracts/run.py` |
| `IBlobStore` / `ISearchIndex` / `ITodoStorage` | `contracts/blob.py` / `contracts/search.py` / `contracts/todo.py` |
| `IToolRegistry` / `Tool` (ABC) | `contracts/tool_registry.py` / `contracts/tools.py` |
| `IToolTransport` | `contracts/resilience.py` |
| `IMemory` / `IWorkspace` | `contracts/memory.py` / `contracts/workspace.py` |
| `ISkillStore` | `contracts/skills.py` |
| `IHookManager` | `contracts/hooks.py` |
| `IEventStream` | `contracts/events.py` |
| `IAgentDispatch` / `IDelegationTool` | `contracts/agent_dispatch.py` |
| `IBackgroundTaskPool` / `IWorkPool` | `contracts/background.py` |
| `IPromptTemplateProvider` | `contracts/prompts.py` |
| `IToolSafetyPolicy` | `runtime/tool_permission.py` |

**Один пул держит оба вида работы.** Хост реализует `IWorkPool` один раз и
получает оба: фоновая команда оболочки и делегированный дочерний прогон — записи
разного `kind` в одном пуле, с одним и тем же id, одинаковым ожиданием и
остановкой через один `WorkHandle`. Ошибиться легко в двух местах. `launch`
выдаёт запись ДО старта работы и передаёт id вашему `start`, поэтому ничто
запущенное вами никогда не работает безымянным. А `stop_session(scope, grace)`
ключуется на владении, а не только на сессии: запись принадлежит `scope`, если
её `owner_scope` равен `scope` либо её `session_id` равен ему, — именно это
позволяет делегированному прогону остановить запущенное им самим, не трогая
команды родителя. `grace` — реальное время, которое ваш handle обязан дать
работе завершиться самой, прежде чем принуждать её.

Делегирующий инструмент объявляет `IDelegationTool`, а не носит атрибут-флаг, и
цикл узнаёт делегирование только по этому.

**Инструменты — особый случай.** Конкретный инструмент — единственная часть,
которую вы пишете *как* код, но он всё равно регистрируется через
`IToolRegistry`, а не встраивается в цикл. Реализуйте ABC `Tool`
(`contracts/tools.py`) напрямую или используйте декоратор `@tool`
(`tools/decorator.py`) для асинхронной функции:

```python
from typing import Any

from protocore import tool, ToolContext, ToolResult
from protocore import IToolRegistry  # the registry interface


@tool(name="echo", description="Echo back the input text.")
async def echo(context: ToolContext, text: str) -> ToolResult:
    # `context` (tenant_id / run_id / session_id / metadata) is injected by the
    # loop and is read-only. Non-`context` params become the JSON-Schema args.
    return ToolResult(tool_call_id=context.run_id, content=text)


def install(registry: IToolRegistry) -> None:
    registry.register(echo())  # the decorator returns a Tool subclass
```

У результата одно значение и несколько адресатов. `ToolResult.content` —
каноническое значение целиком, каким бы большим оно ни было. Три необязательных
поля говорят не о том, что это, а о том, кому и как это показать:

* `model_projection` — текст, который несёт стенограмма вместо `content`.
  Не задан — значение является собственной проекцией, и для почти любого
  инструмента это верно. Задают его, когда короткая запись честна: первая
  страница листинга, «записано 4.2 МБ в `<path>`» для байтов, которые модели
  незачем читать обратно.
* `ui_payload` — структурированные подробности для того, кто смотрит за
  прогоном. Едет на событии результата и в стенограмму не попадает: не стоит
  токенов и не влияет на решение модели.
* `path` — файл, видом которого является результат. Результат, назвавший свой
  файл, рантайм может признать устаревшим: более поздний вызов, переписавший
  этот файл, снимает закрепление с такого результата, вместо того чтобы
  держать перед моделью версию до записи.

```python
return ToolResult(
    tool_call_id=context.run_id,
    content=whole_file,                       # значение
    model_projection=f"{len(lines)} строк",   # что читает модель
    ui_payload={"lines": lines},              # что рисует клиент
    path=path,                                # видом чего это является
)
```

Декоратор выводит `ToolDefinition` (имя, описание, параметры в формате
JSON-Schema) из сигнатуры и docstring; специальный параметр `context:
ToolContext` пропускается при построении схемы. Для единообразия между бэкендами
берите устойчивые, доменно-нейтральные видимые агенту имена-глаголы; см.
[`tools.md`](./tools.md).

**Дополнительные политики безопасности** — тоже точка расширения через
`Protocol`: реализуйте `IToolSafetyPolicy` и зарегистрируйте его в гейте через
`register_policy(...)` (`runtime/tool_permission.py`) — API гейта ядра остаётся
замороженным, пока стек политик растёт во время выполнения (именно так
добавляются `HttpDnsAllowlistPolicy` и `WorkspacePathPolicy`; они **не** входят в
стек по умолчанию).

**Эмпирическое правило:** если в вашем коде есть драйвер базы данных,
HTTP-клиент, проводной формат или любой ввод-вывод, ему место в адаптере за
`Protocol`, а не в `protocore/`.

### Использование шва жизненного цикла

**Когда.** Нужно среагировать в точке прогона — запретить вызов инструмента,
переписать то, что видит модель, наблюдать событие, обернуть работу своим
замером или транспортом — **не** меняя цикл.

Шов **один**, он объявлен в `contracts/middleware.py`. Регистрация называет три
вещи и получает обратно диспозер:

```python
from protocore import HookManager, RegistrationKind
from protocore.contracts.middleware import LifecycleDecision, LifecycleScope, LifecycleVerdict
from protocore.contracts.types import HookEvent

registry = HookManager()
dispose = registry.register(
    HookEvent.pre_tool_use,
    RegistrationKind.decide,
    lambda ctx: LifecycleDecision(verdict=LifecycleVerdict.deny, reason="не этот"),
    owner="my-policy",                       # звучит в каждом вердикте и в логе
    scope=LifecycleScope(tenant_id="acme"),  # необязательно; пусто = «любой»
    priority=50,                             # по возрастанию, затем порядок регистрации
    timeout_s=2.0,                           # только для awaitable-обработчиков
)
...
dispose()          # идемпотентно: второй вызов ничего не делает и вернёт False
```

Реестр передаётся движку при конструировании
(`QueryEngine(..., lifecycle_hooks=registry)`) и работает при включённом
`typed_hooks_enabled`. Это единственный тумблер над швом: ни одна координата не
спрятана за вторым, посторонним.

**Пять видов и что каждому позволено.**

| Вид | Может изменить | При отказе |
|---|---|---|
| `observe` | ничего | логируется, прогон не тронут |
| `decide` | вердикт (`allow` / `deny` / `require_approval` / `fail_run`) | **запрещает** |
| `transform` | полезную нагрузку, и она применяется | **запрещает** |
| `around` | оборачивает работу; может её не выполнить | **запрещает** |
| `notify` | ничего, постфактум | логируется, прогон не тронут |

Разделение намеренное. Шов, существующий чтобы ответить, можно ли, при аварии
или таймауте «да» не сказал — поэтому `decide`, `transform` и `around` падают
**закрыто**. Шов, который только смотрит, не должен уметь менять исход —
поэтому `observe` и `notify` падают **изолированно**: отказ логируется и
попадает в `LifecycleOutcome.failures`, и больше ничего не двигается.

**Координаты** — это члены `HookEvent`, и цикл испускает каждую: `run_start`,
`turn_start`, `context_transform`, `request_prepare`, `response_received`,
`request_error`, `turn_end`, `pre_tool_use`, `tool_execute`, `post_tool_use`,
`pre_compact`,
`compaction_commit`, `compaction_rollback`, `post_compact`, `run_finalize`.
`user_prompt_submit`, `session_start`, `session_end`, `file_changed`,
`subagent_start` и `subagent_stop` доходят до собственного `IHookManager` хоста
(ниже), которого цикл ведёт на гейте разрешений и в диспетчере.

`transform` на `context_transform` применяется: он может вернуть
`system_prompt_sections` (список строк) и `active_language`, и запрос к
провайдеру этого хода пересобирается из возвращённого. Поля, которые он не
назвал, и поля неверной формы оставляют бандл прежним.

**Внепроцессный путь.** `IHookManager` (`contracts/hooks.py`) — контракт для
хуков, чей исполнитель живёт не в этом процессе: HTTP-эндпойнт, модель-судья.
Адаптер даёт хост, цикл зовёт его 3-аргументный
`invoke(event, payload, tenant_id) -> HookResult`, а его `HookActionKind`
`ALLOW` / `DENY` / `MODIFY` отображаются на вердикты выше. Цикл ведёт его на
гейте разрешений и вокруг диспетча инструмента, и там он тоже падает закрыто:
исполнитель, до которого не дозвонились, ничего не разрешал.

`tool_execute` — координата, в которую диспетчер оборачивает сам вызов, и
единственное место, где регистрация `around` охватывает вызов целиком:
обработчик входит до запуска инструмента и продолжается после его возврата,
то есть один обработчик держит весь вызов — таймер, размыкатель, запись. Если
обработчик не дождался своего `next`, инструмент не выполняется, и это читается
как отказ, а не как молчаливый успех: вызов возвращается отказом разрешения с
именем владельца, потому что выдать ответ, которого никто не производил, хуже,
чем сказать «нет». Исключение, таймаут и нечитаемый ответ отказывают так же, а
собственная ошибка инструмента переподнимается как есть — обёртка не может
превратить таймаут в результат, проглотив его.

Самая полезная координата — `pre_tool_use`: это **финальная стадия** гейта
разрешений (порядок гейта: `whitelist` → `safety_policy` → `rate_limit` →
`hook`, в `runtime/tool_permission.py`), точка с наивысшим рычагом, где в
остальном разрешённый вызов переводится в запрет или ставится на одобрение.
Гейт целиком выполняется до предусловий и исполнения
(`runtime/tool_dispatch.py`).

### Сборка состояния прогона и объявление того, что делают инструменты

**Используйте, когда** вы вообще встраиваете цикл: это не дополнительные
возможности, а пара, которую поставляет каждый хост.

`RunScopedState` (`contracts/run_state.py`) — то, что прогон несёт при
исполнении. Хост собирает его на старте, кладёт свои пер-прогонные слоты в отсек
`host`, который ядро не читает и не пишет, и передаёт движку. Дальше каждый вызов
инструмента достаёт его как `ToolContext.run_state`, а дочерний прогон наследует
по ссылке то, что разделяет всё дерево.

```python
from protocore.contracts.run_state import RunScopedState

state = RunScopedState(
    rc=constants,                      # снапшот констант этого прогона
    cancel_event=asyncio.Event(),      # то, что выставляет ваш путь отмены
    host={"workspace": workspace},     # ваши слоты; цикл их игнорирует
)
engine.run_state = state
```

`ToolRoleMap` (`contracts/tool_roles.py`) говорит, что делают ваши инструменты.
Цикл никогда не читает имя инструмента, чтобы что-то решить: он спрашивает карту.
Объявите её один раз там, где инструменты регистрируются, — роль на инструмент и
написания аргументов, под которыми приходит каждое значение, потому что рантайм
видит аргументы такими, какими их выдала модель, до того как входная модель
вашего инструмента разрешит алиас.

```python
from protocore.contracts.tool_roles import ToolArgumentSlot, ToolRole, ToolRoleMap

roles = ToolRoleMap.declare(
    {
        "put_file": [ToolRole.writes_path],
        "open_file": [ToolRole.reads_path],
        "spawn": [ToolRole.delegates_work, ToolRole.never_delegated],
    },
    argument_aliases={ToolArgumentSlot.path: ["path", "file_path"]},
)
```

Необъявленная роль — это поведение, которое замолкает: не названный картой
пишущий инструмент перестаёт снимать закрепление с устаревших прочтений, а
shell-инструмент с необъявленным написанием команды отправляет свои вызовы на
одобрение, вместо того чтобы выполнять их непроверенными.

Скажите также, кто написал то, что вы кладёте в историю. Ядро считает обычное
сообщение роли user словами оператора; хост, который доставляет по этому каналу
свои события или ответы оператора по другому каналу, помечает их ключом
`OPERATOR_WORDS_METADATA_KEY`, и компакция цитирует слова оператора в реестре
целиком, а остальное сжимает как любое другое сообщение (таблица — в
[контракте компакции](compaction.md#кто-написал-сообщение)):

```python
from protocore.contracts.types import OPERATOR_WORDS_METADATA_KEY, Message, MessageRole, TextBlock

answer = 'the operator answered request [a1b2] "Which port?": 8443'
note = Message(
    role=MessageRole.user,
    content_blocks=[TextBlock(text=f"2 events:\n- build 412 finished\n- {answer}")],
    metadata={OPERATOR_WORDS_METADATA_KEY: [answer]},  # True: всё; False: ничего
)
```

### Добавление флага `LoopConstants`

**Используйте, когда** изменение — это настраиваемое значение или переключатель
вкл/выкл, а не новый поток управления. Каждая настройка в ядре проходит через
`LoopConstants` — **замороженный Pydantic-снимок** с `model_config =
ConfigDict(frozen=True, extra="forbid")` (`contracts/runtime_constants.py`).
**Никаких встроенных магических чисел** — код рантайма читает из снимка, а не из
жёстко зашитого литерала.

Новые возможности по умолчанию **выключены** (или установлены в значение,
воспроизводящее прежнее поведение), чтобы тенант подключал их осознанно.
Добавление настройки — это **одна правка**: добавьте поле с его default-ом,
границами и обращённым к оператору `description` в ту модель, чей слой его
читает. Для порога, который читает цикл, эта модель — `LoopConstants`; ручка,
которую читает окружающий слой, принадлежит собственной модели этого слоя и его
собственной группе констант. В любом случае группа отражается из модели
(`group_from_model`, `contracts/config.py`), поэтому каталог оператора
подхватывает поле без второй регистрации, которую пришлось бы держать в
согласии.

Поскольку `extra="forbid"` отклоняет неизвестные поля, **ядро и
хост должны развёртываться парно** — поле, добавленное на одной стороне без
другой, отклонит снимок. Полную модель, реестр и три состояния видимости ручки
см. в [`runtime-constants.md`](./runtime-constants.md).

Если ваша «фича» на самом деле — «дать тенанту включать/выключать X» или «дать
тенанту задать порог для Y», поле и есть всё изменение — никакая другая точка
расширения не нужна.

### Внедрение секции системного промпта

**Используйте, когда** хотите добавить статический текст в системный промпт
модели — персону, доменное руководство, блок ориентира — который должен
присутствовать в прогоне всегда. Они передаются при конструировании движка через
`QueryEngineConfig.system_prompt_sections` (`tuple[str, ...]`,
`runtime/query_engine.py`); цикл собирает их в системное сообщение на каждом
шаге.

Это правильная точка расширения для *содержимого промпта*. Это **не** правильная
точка расширения для поведения, которое должно реагировать на события
(используйте hook), для значения, которое должно настраиваться тенантом
(используйте флаг RC), или для динамического пошагового ориентира, считываемого
из окружения (это путь RC `context_bootstrap_*`, см. раздел
[Hooks](./architecture.md)).

Стоит знать о нескольких смежных точках внедрения на `QueryEngineConfig` — это
**внедряемые вызываемые объекты, карты и наблюдатели**, а не текст промпта:
`cache_observer` (`CacheObserverProtocol`, приёмник доли попаданий
prompt-кэша), `request_manifest_sink` (`IRequestManifestSink` — где хранится
запись о том, что было отправлено провайдеру), `resilience_classifier`
(`IResilienceClassifier` — к какому нейтральному классу отказа относится
сообщение), `tool_roles` (`ToolRoleMap` — что ДЕЛАЮТ инструменты хоста и какими
написаниями аргументов) и два вызываемых триггера терминальной верификации
(`pre_terminal_self_verify_trigger`, `pre_dispatch_terminal_verify_trigger`). Все
по умолчанию `None` / пусты, поэтому стоящая за каждым механика инертна, пока
хост его не внедрит, — а для тех, что закрыты RC, ещё и не переключит поле.

### Подстановка политики хода

**Используйте, когда** изменение — это продуктовое решение, которое принимает
драйвер хода: что прогон исчерпал бюджет, что пустой ответ заслуживает ещё одной
попытки, что недописанный файл надо запечатать прежде, чем прогону позволят
закончиться. До появления шва каждое из них было веткой, выращенной внутри
драйвера, и изменить одно, не редактируя цикл, было нельзя.

Политика — объект с `name`, списком `coordinates`, на которых её надо
спрашивать, и одним `apply(turn)`, который выдаёт события для проброса и пишет
дальнейшее в `turn.outcome` — `proceed`, `restart_turn` или `end_turn`. Она
читает и меняет прогон через `ITurnState` — намеренно узкий структурный вид:
политика, которой нужно что-то, не названное там, лезет во внутренности цикла, и
ревью, добавляющее имя, — то самое место, где это будет замечено.

```python
engine.turn_policies = core_policies.merged_with(
    TurnPolicyRegistry((OurRunCeilingsPolicy(...),))
)
```

Смысл шва — в двух свойствах. **Порядок принадлежит ядру**, объявлен один раз в
`TURN_POLICY_ORDER`, потому что порядок важен там, где две политики встречаются,
а порядок, собранный тем, кто строил список, сделал бы это совпадением; политика,
имени которой в этом кортеже нет, отвергается при построении, а не уезжает молча
в конец. И набор **сливается по имени**, а не подставляется вместо: ваша политика
вытесняет политику ядра с тем же именем, а всякая граница, которую никто не
назвал, остаётся на месте. Замена всего реестра унесла бы с собой собственные
потолки ядра — ровно тот отказ, который слияние и предотвращает.

## Жёсткие правила (не нарушайте их)

Два правила ограничивают любое расширение. Нарушение любого из них — провал
процесса, а не выбор дизайна.

### Не изменяйте структуру цикла

ReAct-цикл (`runtime/query.py` + `runtime/query_engine.py` +
`runtime/loop_state.py`) **неизменяем**. Это единственный потребитель всех прочих
подсистем и основа межподового снимка/возобновления. **Не редактируйте его
структуру.** Настраивайте только через четыре точки расширения, перечисленные
выше:

- **hook-и** (запретить/изменить/наблюдать в точках жизненного цикла),
- **`QueryEngineConfig`** — внедряемые вызываемые объекты/наблюдатели,
- флаги **`LoopConstants`**,
- **`system_prompt_sections`**.

Если изменение, кажется, требует новых ветвлений в цикле хода, это сигнал, что вы
выбрали неправильную точку расширения — перепроверьте [порядок принятия
решения](#выбор-точки-расширения). Поведение восстановления, терминальная
классификация и финализация — всё уже под управлением RC; вы их переключаете, а
не переписываете.

### Никогда не импортируйте вверх (граница импорта)

Ядро — **корень** графа зависимостей и никогда не должно импортировать вверх.
`protocore/` никогда не должен импортировать пакет, чьё имя начинается с
`protocore_`: это подчёркивание и отмечает соседний дистрибутив над ядром —
адаптеры, сервисный слой, фронтенды, бэкенд исполнения, средства развёртывания.

Добавляйте поведение через **контракты / адаптеры / RC**, а не тянитесь вверх.
Если ядру нужно что-то из вышестоящего слоя, выразите эту потребность как новый
`Protocol` и дайте хосту внедрить реализацию.

Это обеспечивается guard-тестом
[`tests/test_core_import_boundary.py`](../tests/test_core_import_boundary.py). Он
обходит каждый файл `*.py` под `protocore/`, разбирает AST и **роняет CI**, если
любой `import` / `from … import` на верхнем уровне ссылается на запрещённый
пакет. Запустите его (и остальной набор тестов) перед пушем — см.
[`testing.md`](./testing.md).
