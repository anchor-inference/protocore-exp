# MCP — инструменты MCP-сервера как инструменты ядра

> Аудитория: хост, которому нужны в прогонах инструменты сервера Model
> Context Protocol.
> Код: `protocore/mcp/` (`session.py` — клиент JSON-RPC, `stdio.py` и
> `http.py` — транспорты, `tools.py` — сервер и прокси его инструментов).

`protocore.mcp` подключается к MCP-серверу, публикует его инструменты в
реестре инструментов одной откладываемой группой и пересылает вызовы модели.
Больше ничто в ядре его не импортирует.

```bash
pip install "protocore[mcp]==2.0.0a25"   # добавляет httpx для HTTP-транспорта
```

Транспорту stdio ничего не нужно; транспорту streamable HTTP нужен `httpx`,
который ставит набор `mcp`. Клиент написан в ядре, а не взят из официального
MCP SDK: адаптеру инструментов нужна малая часть протокола (рукопожатие,
`tools/list`, `tools/call`, `ping`, уведомление о смене списка
инструментов), а SDK приносит веб-сервер, библиотеку JWT и телеметрию в
каждый хост, которому нужно лишь вызвать несколько инструментов. Хост, у
которого SDK уже работает, может передать свой транспорт (ниже).

## Сервер в пять строк

```python
from protocore.mcp import McpServer

tracker = McpServer.stdio(
    "tracker", "tracker-mcp", ["--project", "core"],
    env={"TRACKER_TOKEN": token},
    registry=registry,
    search_hint="issue bug ticket report",
)
await tracker.start()      # необязательно: первый вызов тоже подключает
...                        # прогоны видят инструменты Mcp_Tracker_*, придержанные за ToolSearch
await tracker.close()      # останавливает сервер и убирает его инструменты
```

`McpServer.http(name, url, *, headers=None, auth=None, **options)` — то же
поверх streamable HTTP. Оба — сокращения для
`McpServer(name, transport_factory, **options)`, где фабрика строит свежий
`McpTransport` для каждого подключения.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `registry` | `None` | куда публикуются инструменты; без него читайте их из `server.tools` |
| `description` | заголовок сервера | строка группы в каталоге (одна строка, 200 символов) |
| `search_hint` | `""` | добавляется к подсказке поиска каждого инструмента вместе с его заголовком |
| `load` | `"auto"` | режим загрузки группы: `eager`, `auto`, `lazy` |
| `group_name` | `"MCP server <name>"` | имя группы |
| `name_prefix` | `Mcp_<Name>_` | префикс имени каждого инструмента и префикс группы |
| `call_timeout_seconds` | 120 | сколько может длиться один вызов |
| `connect_timeout_seconds` | 30 | сколько может длиться подключение с рукопожатием |
| `client_name` | `"protocore"` | `clientInfo.name`, отправляемое при рукопожатии |

## Инструменты, группы и откладывание

Каждый удалённый инструмент становится `McpTool` с именем
`<prefix><удалённое имя>`, где каждый символ вне `[A-Za-z0-9_-]` заменён на
`_`, обрезанным до 64 символов; два удалённых имени, давшие одно и то же,
получают `_2`, `_3`. Инструменты сервера объявляются одной **динамической**
группой (`declare_group(..., dynamic=True, prefix=...)`): её состав задаёт
внешний сервер, а не код хоста, поэтому цикл придерживает её первой и
называет одной строкой каталога, а модель загружает нужные инструменты
через `ToolSearch` (см. [Отложенные группы инструментов](tools.md#отложенные-группы-инструментов)).
Собственные `instructions` сервера из рукопожатия становятся `instructions`
группы и пишутся рядом с инструментами только тогда, когда те загружены.
Группа объявляется заново с каждым списком, так что изменённое описание
доходит до следующего прогона, и снимается вместе с последним инструментом:
оставшееся объявление заняло бы префикс сервера, добавленного позже под тем
же именем.

Каждый инструмент несёт `tool_group` (свою группу, явно), `search_hint` и
`output_trust = "untrusted"`: его вывод — текст, написанный внешним
сервером, и среда, которая огораживает недоверенный вывод, огородит и его.

## Схемы

`properties`, `required` и булево `additionalProperties` попадают в
определение инструмента, так что строгая схема сервера остаётся строгой на
проводе. Локальные ссылки `$ref` в `$defs` или `definitions` подставляются
на место, потому что схема ядра не хранит раздела определений, а ссылка в
никуда — это схема, которой не удовлетворит ни одна модель; рекурсивная
схема подставляется на восемь уровней вглубь и ниже остаётся открытой.
`additionalProperties`, заданное схемой, некуда положить в поле ядра, и оно
опускается — это разрешающее прочтение, а сервер всё равно проверяет то, что
получает.

## Результаты и ошибки

| Сервер возвращает | Результат инструмента |
|---|---|
| содержимое `text` | текст, по блоку на строку |
| `image`, `audio` | `[image image/png returned by the tool]`; изображение ещё и прикладывается как `ToolResult.images`, так что модель со зрением его видит |
| `resource_link` | `[resource <name>: <uri>]` |
| встроенный `resource` | его текст или `[binary resource <uri> (<type>)]` |
| `structuredContent` | сам результат, когда текста нет, иначе `ui_payload["structured_content"]` |
| `isError: true` | результат-ошибка (`is_error=True`), текст как его написал сервер |
| ничего | `(empty result)` |

`metadata` результата называет сервер и удалённый инструмент. Всё, что не
является собственным ответом инструмента, бросает `ToolInvocationError` —
контракт ошибок инструментов ядра, который диспетчер превращает в
результат-ошибку, читаемый моделью:

- ошибка протокола (неизвестный инструмент, неверные аргументы) — с кодом,
  сообщением и данными сервера;
- нет ответа за `call_timeout_seconds` — серверу уходит
  `notifications/cancelled`, а сообщение говорит, что неизвестно, сработал
  ли вызов;
- соединение оборвалось во время вызова — неизвестно, сработал ли он, и
  сообщение просит модель проверить, прежде чем вызывать снова;
- сервер недоступен — вызов не отправлялся.

## Жизненный цикл

`start()` подключается, проходит рукопожатие, получает список инструментов
(следуя `nextCursor`) и публикует их; одновременные запуски открывают одно
подключение. `stop()` закрывает подключение и оставляет инструменты
опубликованными, так что следующий вызов переподключится. `close()` ещё и
убирает инструменты и группу.

Вызов, который застал подключение закрытым, переподключается один раз до
отправки: по оборванному подключению ничего не уходило, значит, ничего не
повторится. Вызов, чьё подключение оборвалось, пока он был в пути, не
повторяется, потому что сервер мог его выполнить. `state` (`stopped`,
`connecting`, `ready`, `failed`) и `error` говорят, в каком состоянии сервер.

Сервер, приславший `notifications/tools/list_changed`, опрашивается заново,
и реестр обновляется в фоне. `refresh_tools()` делает это по запросу —
HTTP-транспорт не открывает поток для сообщений по инициативе сервера, так
что по HTTP о смене слышно только внутри ответа на какой-нибудь запрос.

## Транспорты

**stdio** (`StdioTransport(command, args, *, env=None, cwd=None)`) запускает
сервер дочерним процессом и говорит с ним JSON, разделённым переводами
строк, через стандартные потоки. Процесс наследует из окружения хоста лишь
несколько переменных (`INHERITED_ENVIRONMENT`: `HOME`, `PATH`, `USER`, локаль
и ещё немного) плюс то, что названо в `env`, так что ключи хоста не утекают
серверу, которому их не давали. Строки до 32 МиБ читаются целиком; то, что
сервер пишет в stderr, уходит в отладочный лог; строка в stdout, не
являющаяся JSON, пропускается. При закрытии закрывается stdin, затем процесс
получает terminate и, если не завершился, kill.

**Streamable HTTP** (`StreamableHttpTransport(url, *, headers=None,
auth=None, client=None)`) отправляет каждое сообщение POST-запросом и читает
ответ как JSON или как поток SSE, который может до ответа нести собственные
уведомления и запросы сервера. Выданный при рукопожатии `Mcp-Session-Id` и
согласованная `MCP-Protocol-Version` идут в каждом следующем запросе, а при
закрытии сессия завершается запросом `DELETE`. `auth` — асинхронная
функция, возвращающая заголовки; она вызывается при каждом подключении, так
что обновлённый bearer-токен подхватывается при переподключении. Отказ
(`McpHttpError` со своим `status`) завершает сессию: `401` значит, что токен
надо обновить, `404` — что сервер забыл сессию; следующий вызов
переподключится. Перенаправления не выполняются, потому что запросы могут
нести учётные данные.

**Свой.** Всё, у чего есть `open()`, `send(message)`, `receive()`,
`negotiated(protocol_version)` и `close()`, — это `McpTransport`: например,
мост к сессии SDK, которая у хоста уже есть, или сервер внутри процесса в
тестах. Передайте `lambda: MyTransport(...)` как фабрику.

## Сессия

`McpClientSession(transport, *, client_name, client_version,
request_timeout, on_tools_changed)` — клиент JSON-RPC под `McpServer`,
пригодный и сам по себе: `start()`, `list_tools()`,
`call_tool(name, arguments, timeout=)`, `request(method, params)`,
`notify(method, params)`, `close()`. Он предлагает ревизию протокола
`2025-11-25` и принимает ревизии из `SUPPORTED_PROTOCOL_VERSIONS`; сервер,
ответивший другой, получает отказ с `McpError`, а не понимается наполовину.
Он отвечает на `ping` сервера и отказывает другим запросам сервера
(sampling, roots, elicitation) с «method not found», поскольку не объявлял
этих возможностей. Ответ-ошибка бросает `McpError(code, message, data)`;
пропавшее соединение бросает `McpTransportClosed` каждому ждущему и
последующему запросу.

## Что не охвачено

Потоки OAuth (хост получает токен сам и передаёт его через `auth`), старый
транспорт HTTP+SSE, ресурсы и промпты, sampling и elicitation, а также
HTTP-поток `GET` для сообщений по инициативе сервера.
