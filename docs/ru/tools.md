# Поверхность инструментов

> Аудитория: инженер, который добавляет инструменты, доступные агенту, в
> **чистом ядре** (`protocore/`), или рассуждает о них.
> Область: текущая библиотека ядра (`protocore/`). Ядро владеет
> *контрактами, именами, диспетчеризацией, гейтингом, извлечением и порядком*
> инструментов. Оно поставляет несколько конкретных инструментов, вся
> поверхность которых **является** контрактом протокола, — ask-user
> (`tools/ask_user.py`), память (`tools/memory.py`) и поиск инструментов
> (`tools/tool_search.py`), — но **не** регистрирует
> ни одного конкретного
> инструмента по умолчанию (sandbox / exec / read / write); эти
> продакшен-инструменты, привязанные к бэкенду, живут у хоста. (**Контракт** `IWorkspace` живёт в ядре, но его конкретные
> инструменты — только в хосте; см. подсистему рабочего пространства в
> [`architecture.md`](architecture.md).)
> Более широкую картину см. в [`architecture.md`](architecture.md).

Ядро намеренно держит список инструментов, видимых агенту, **маленьким и
стабильным**: небольшой универсальный пул делает промпт дешёвым для меньших
локальных моделей, а детерминированный порядок сохраняет переиспользуемость
KV-prefix-кэша между ходами. Для поверхности по умолчанию
(sandbox / exec / read / write) ядро не регистрирует ни одного конкретного
инструмента — оно определяет *форму* и механику, которая безопасно выполняет
один вызов инструмента, а хост привязывает реализации, обеспеченные
бэкендом. (Ядро всё же поставляет собственные инструменты поверхности протокола —
ask-user, память и поиск инструментов, — см. [замечание об области](#поверхность-инструментов)
выше.)

## Декоратор `@tool`

`tools/decorator.py` предоставляет лёгкий внутриядерный помощник, превращающий
асинхронную функцию в подкласс `Tool`. Pydantic-овский `TypeAdapter` выводит
JSON-схему параметров из аннотаций типов функции; особый параметр
`context: ToolContext` пропускается. Декорируемый вызываемый объект
**заменяется** сгенерированным подклассом `Tool`.

`tool`, `ToolContext` и `ToolResult` реэкспортируются на верхнем уровне пакета:

```python
from protocore import tool, ToolContext, ToolResult


@tool(name="echo", description="Echo back the input.")
async def echo(context: ToolContext, text: str) -> ToolResult:
    return ToolResult(tool_call_id="...", content=text)
```

Результат несёт своё каноническое значение и, рядом с ним, проекции для
модели и для клиента — см. [«Расширение ядра»](./extending.md),
где эти поля разобраны с примером.

Оборачиваемая функция должна быть `async` — иначе `@tool` поднимает `TypeError`.
`echo` теперь является подклассом `Tool`, чей `.definition` несёт `name`,
`description` и схему, построенную из аннотации `text: str`. Инструменты
по умолчанию, обеспеченные бэкендом, используют этот декоратор, но живут у
хоста; само ядро не регистрирует ни одного из них (хотя оно поставляет
инструменты поверхности протокола ask-user / память). Для более богатых или stateful-инструментов
реализуйте ABC `Tool` (`contracts/tools.py`) напрямую.

## Конвейер диспетчеризации

`runtime/tool_dispatch.py` — `ToolDispatcher.dispatch(...)` является **единственной
точкой входа в ядро** для выполнения одного `ToolCall` после того, как LLM
закончила его эмитировать. Диспетчер агностичен к реализации инструмента: он
зависит только от `Tool.invoke`. Он **никогда не поднимает исключение** при
ошибке инструмента — каждый режим отказа транслируется в блок
`tool_result(success=false)`, чтобы модель могла восстановиться на следующем ходу,
а запуск никогда не падал жёстко.

`dispatch()` — это асинхронный генератор, который выдаёт конверты `TurnEvent` и,
последним элементом, `DispatchOutcome`. Жизненный цикл:

1. **Поиск в реестре** — `DispatchErrorKind.unknown_tool`, если имя не
   зарегистрировано.
2. **Валидация схемы** — инвариант ограничения по байтам / JSON-сериализуемости
   на входном словаре (специфичная для инструмента Pydantic-валидация живёт в
   корпоративном адаптере).
3. **Гейт разрешений** — расходится на `ToolPermissionGate.check(...)` (ниже).
   Вердикт `require_approval` поднимает событие `tool_call_pending` и не выдаёт
   результата инструмента; вызывающая сторона переводит цикл в `AWAITING`.
4. **Предусловия** — проверяется DAG `ToolDefinition.preconditions` инструмента
   (ниже); неудовлетворённый инструмент срабатывает накоротко с отказом, когда
   установлен `LoopConstants.tool_preconditions_enabled`.
5. **Выполнение** — `tool.invoke(ctx)`, обёрнутый в `asyncio.wait_for` с учётом
   `rc.tool_timeout_seconds`.
6. **Координата `post_tool_use`** — fire-and-await; может переписать вывод.
   Срабатывает ровно один раз для каждого вызова, у которого есть результат,
   включая каждый отказ выше (неизвестный инструмент, валидация, запрет,
   невыполненное предусловие, таймаут, поднятое исключение, нечитаемая форма
   результата). Пропускает её только вызов, поставленный на одобрение или на
   ответ пользователя: результата у него ещё нет. См.
   [полезную нагрузку хука](#полезная-нагрузка-post_tool_use).

`DispatchOutcome` (frozen) несёт `success`, `content`, `is_error`,
`error_kind`, `approval_required` / `approval_token`, `ask_user_required` /
`ask_user_payload`, `duration_ms` и набор `metadata`. `DispatchErrorKind` — это
таксономия отказов: `validation | permission | execution | timeout |
rate_limit | unknown_tool | consecutive_error_cap`. Последний — это страховка:
как только серия идущих подряд одинаковых ошибок в рамках запуска превышает
`tool_dispatch_consecutive_error_cap`, диспетчер переписывает отказ в этот вид,
чтобы застрявший цикл завершился вместо сжигания итераций.

Инструмент может прикрепить к поднятому исключению машиночитаемый словарь
`structured_error` (например, `{"finalization_recommended": True, "reason": ...}`);
ветка except в диспетчере прокидывает его на `DispatchOutcome.metadata`, и цикл
поднимает модели подсказку о финализации.

### Полезная нагрузка `post_tool_use`

`IHookManager` хоста получает `run_id`, `tenant_id`, `tool_call_id`,
`tool_name`, `tool_output` (текст, который прочтёт модель), `success`,
`is_error`, `error_kind` и `duration_ms`. `error_kind` равен `None` при успехе,
а иначе — значению `DispatchErrorKind`, которое увидит модель. Оно берётся
после ограничения серии одинаковых ошибок, так что ограниченный отказ
приходит как `consecutive_error_cap` с исходным текстом внутри. Собственный
`ToolResult(is_error=True)` инструмента приходит как `execution`.

Текст отказа — часто единственное место, где всплывает секрет: командная
строка с токеном в исключении, URL с учётными данными, сервер, повторивший
отвергнутый ключ. Поэтому отказ проходит через хук так же, как успех.
`MODIFY` со строковым `tool_output` заменяет текст в `DispatchOutcome`, в
событии `tool_result` и в блоке истории, а значит, во всех последующих
запросах и снимках. Копия текста ошибки, которую метаданные результата хранят
для параллельного воспроизведения, тоже заменяется, и выставляется
`tool_dispatch.post_tool_output_modified`. Хук, которому нужны только успехи,
возвращает `ALLOW`, когда `is_error` истинно. Хук, поднявший исключение,
логируется и игнорируется на обоих путях, и результат остаётся как был.

Переписывание заканчивает и собственное значение инструмента: оригинал не
должен пережить процесс, поэтому `canonical_content` отбрасывается, и дальше
значением служит текст хука. Результат сверх лимита на входе выгружается как
переписанный текст, никогда как оригинал. `canonical_ref`, который инструмент
сохранил сам, тоже отбрасывается, потому что ядро не может замаскировать то, на
что он указывает, как и `ui_payload`, которого хуку не показывают; хост, которому
нужно сохранить одно из них, должен замаскировать его до возврата из
инструмента. `path` остаётся. Хук, вернувший `ALLOW`, или `MODIFY` без
строкового `tool_output`, оставляет всё это как было.

`tool_output` — проекция для модели. Когда инструмент задаёт
`model_projection`, каноническое значение за ней в полезную нагрузку не входит
и, если хук не переписал вывод, сохраняется; инструменту, чьё каноническое
значение может нести секрет, не стоит прятать его за проекцией, сквозь которую
хук не видит.

См. раздел [Tool dispatch + gating](architecture.md) о контракте эмиссии
событий.

## Гейт разрешений

`runtime/tool_permission.py` — `ToolPermissionGate.check(...)` запускает
асинхронный конвейер и возвращает **первое не-allow** решение
`ToolPermissionDecision`. Поле `outcome` решения — одно из `allow` / `deny` /
`require_approval`, с опциональным переписанным `modified_input` и
`approval_token`. Каждое решение также фиксирует `PermissionStage`, на котором оно
было достигнуто (для телеметрии).

StrEnum `PermissionStage` именует четыре упорядоченные стадии гейта плюс
no-op-значение по умолчанию:

| Порядок | Стадия (`PermissionStage`) | Что проверяет |
|---|---|---|
| 1 | `whitelist` | `ToolVisibilityPolicy` (и любой сужающий whitelist субагента) должен разрешать имя инструмента — `blocked` всегда запрещает, `visible` (когда непуст) является строгим allow-list. |
| 2 | `safety_policy` | Проверки по классу побочных эффектов через цепочку `IToolSafetyPolicy`. |
| 3 | `rate_limit` | Только хост; базовая линия — no-op `allow`. Скомпонуйте политику бакета на Redis через `register_policy`, чтобы запрещать здесь. |
| 4 | `hook` | Координата `pre_tool_use` — финальная, наиболее рычажная стадия; может перевернуть `allow` → `deny` / `require_approval` либо изменить аргументы. Пропускается, когда менеджер хуков не подключён. |
| — | `default` | Значение StrEnum по умолчанию, используемое для неявного `allow`, когда ни одна стадия не возразила. |

Политика безопасности реализует `IToolSafetyPolicy` —
`applies_to(side_effect_class)` плюс `evaluate(tool, arguments, ctx)`. Стек
политик по умолчанию содержит ровно одну политику:

- `ShellSafetyPolicyAdapter` — обёртка вокруг `DefaultShellSafetyPolicy`,
  инспектирующая тот аргумент, который хост объявил командой шелла, у
  инструментов с ролью `runs_shell`. Инструмент, написание команды которого не
  объявлено, отправляется на одобрение, а не выполняется без разбора: проверку
  нельзя пропустить только потому, что ядро не знает, куда смотреть.

`HttpDnsAllowlistPolicy` и `WorkspacePathPolicy` предоставлены, но **не** входят
в стек по умолчанию; хост передаёт стек, который применяют его прогоны, как
`QueryEngine(tool_safety_policies=...)` — `None` для стека по умолчанию выше,
`[]` ни для какого, список — ровно для этих политик (см.
[`extending.md`](./extending.md)). Гейт всегда включён. Хук
Координата `pre_tool_use` — наиболее рычажный шов для гейта вида LLM-as-policy.

См. раздел [Permission gate](architecture.md) о месте гейта в потоке
диспетчеризации и о карте классов побочных эффектов.

## Трёхслойная эффективная поверхность

`runtime/tool_registry.py` — `ToolRegistry` реализует контракт `IToolRegistry`
(`contracts/tool_registry.py`). Его `compute_effective_surface(...)` — это
фильтр на каждый ход, удерживающий список инструментов LLM маленьким и
релевантным, сохраняя при этом байт-детерминированный порядок. Цикл вызывает его
каждый ход, и он применяет три слоя:

1. **Политика** — применяет `ToolVisibilityPolicy` (allow-list `visible` /
   deny-list `blocked` / всегда включаемые `pinned`), давая видимый набор
   тенанта.
2. **Отсечение** — если `top_k is None` или незакреплённых инструментов уже
   `<= top_k`, возвращает набор отсортированным по имени (никакого извлечения
   вовсе).
3. **Прогрессивное обнаружение** — иначе всегда включает инструменты `pinned`,
   `forced_pinned` и `always_load` и добавляет `top_k` лучших по рангу из
   остальных для недавнего запроса пользователя `query` (см.
   [Поиск инструментов](#поиск-инструментов)). Закреплённые инструменты в
   `top_k` не входят; раньше входили, и пол размером с порог по умолчанию не
   оставлял отсечению места ни для одного найденного инструмента.

```python
def compute_effective_surface(
    self,
    tenant_id: str,
    policy: ToolVisibilityPolicy,
    *,
    query: str = "",
    top_k: int | None = None,
    retrieval: RetrievalSettings | None = None,
) -> Sequence[ToolDefinition]: ...
```

Какой бы слой ни сработал, **финальный порядок всегда по возрастанию имени** —
порядок извлечения управляет *отбором*, но эмитируемый список сортируется по
имени, так что контекст LLM остаётся байт-стабильным, а KV-prefix-кэш переживает
ходы. Порог отсечения — это RC `tool_retrieval_top_k`, передаваемый циклом
(`0`, значение по умолчанию, выключает отсечение, см.
[почему](#почему-не-стоит-отсекать-по-сообщению); реестр читает `top_k=0` так
же, как `None`, поэтому хост может передавать константу как есть), а
`retrieval` — это `RetrievalSettings.from_constants(rc)`.

Цикл не отправляет этот список как есть. `runtime/tool_deferral.py` строит из
него инструменты запроса: убирает группы, которые прогон
[откладывает](#отложенные-группы-инструментов), и дописывает после него
найденные прогоном инструменты в порядке их обнаружения.

`ToolRegistry.search(query, top_k=...)` — путь, которым пользуется инструмент
вроде `ToolSearch`, — отличается в одном: он возвращает инструменты **в порядке
ранга**, лучший первым, при равенстве — по имени. Результат поиска модель читает
один раз, и порядок — единственный способ узнать, какое совпадение лучше.

## Поиск инструментов

`runtime/tool_retrieval.py` ранжирует инструменты лексически, на чистом Python,
без зависимостей сверх стандартной библиотеки. Один и тот же движок обслуживает
и отсечение на каждом ходу, и `search`.

**Что индексируется.** У каждого инструмента пять полей: имя, `search_hint`,
первое предложение описания, остаток описания, имена и описания параметров.
Подсказка и параметры нужны только для поиска; ни то, ни другое не попадает в
схему, которую видит модель. Первое предложение кончается точкой, `!` или `?`
перед пробелом, но не точкой внутри скобок и не точкой сокращения (`e.g.`,
`i.e.`, `vs.`, `т.е.`, `напр.`; `etc.` и `т.д.` — только перед заглавной
буквой): это же предложение `ToolSearch` показывает строкой инструмента, а
строка, оборванная на «(e.g.», модели ничего не говорит.

**Как разбирается текст** (`runtime/text_analysis.py`, одинаково для каталога и
для запроса):

- идентификаторы разбиваются — CamelCase, `snake_case`, `kebab-case`, пути через
  точку, граница буквы и цифры — и склеенная форма тоже сохраняется, так что
  `BrowserOpen` находится и по `browser open`, и по `browseropen`, как и
  склеенная форма каждого хвоста частей, так что `get_issue` находит
  `mcp__github__get_issue` раньше других инструментов задач того же сервера;
- текст приводится к нижнему регистру, `ё` пишется как `е`;
- отбрасываются английские и русские стоп-слова, включая разговорные вставки
  ("please", "слушай", "короче", "плз");
- слова стеммируются (`runtime/stemmers.py`): Snowball Russian для кириллицы,
  исходный алгоритм Портера для английского. Токены короче трёх букв не
  трогаются.

**Как оценивается запрос.** BM25F: частота термина в каждом поле нормируется
на среднюю длину этого поля, взвешивается, суммируется по полям и один раз
насыщается. Веса и параметры BM25 — константы:

| Константа | По умолчанию |
|---|---|
| `tool_retrieval_name_weight` | 1.0 |
| `tool_retrieval_search_hint_weight` | 1.0 |
| `tool_retrieval_summary_weight` (первое предложение) | 1.0 |
| `tool_retrieval_description_weight` (остальное) | 0.6 |
| `tool_retrieval_parameters_weight` | 0.3 |
| `tool_retrieval_bm25_k1` | 1.5 |
| `tool_retrieval_bm25_b` | 0.3 |
| `tool_retrieval_lexicon_weight` | 0.5 |

Они подобраны вместе кросс-валидацией на размеченных английских и русских
запросах к каталогу примерно из 700 инструментов. С выключенным лексиконом вес
подсказки 2 работает лучше, чем 1.

**Русские запросы к английским инструментам.** Русский запрос не делит ни одного
слова с английским описанием. Реестр расширяет каждую русскую основу запроса до
английских основ, в которые она переводится, с весом
`tool_retrieval_lexicon_weight` относительно собственных терминов запроса.
Лексикон поставляется как данные пакета (`runtime/tool_retrieval_lexicon.json`,
около двух тысяч английских слов с русскими соответствиями); это общая лексика
разработчика, переведённая с английского языка описаний инструментов, а не с
запросов. Только он позволяет русскому запросу найти сторонний инструмент, у
которого никогда не будет русской подсказки, поэтому в нём есть и заимствования
и сленг, которыми русскоязычный разработчик называет лексику трекеров, чатов,
календарей и деплоя, — «пулреквест», «ишью», «таска», «смержи», «выкати»,
«созвон», «алерт»: их нет ни в одном словаре, а английский MCP-серверов состоит
из них. Глаголы в нём записаны инфинитивом, а просьба обычно звучит в
повелительном наклонении, и стеммер не сводит «редактировать» и «редактируй» к
одной основе; поэтому каждый инфинитив регистрируется и под основами своих
императивов, а основа, которой в лексиконе нет, ищется ещё раз без
приставки совершенного вида («отредактируй», «скопируй»). Хост передаёт свой через
`ToolRegistry(lexicon=Lexicon.from_translations(...))` или выключает расширение
через `lexicon=None` либо нулевой вес.

**Когда ничего не набрало очков**, второй этап сопоставляет нестрогие подстроки
и общие префиксы (`normalized_fallback_match`) — так находится часть имени
инструмента или словоформа, которую стеммер не сводит. Он работает и для
`search`, и для отсечения.

**Стоимость.** Разобранный каталог и константы оценки строятся один раз на
версию каталога и набор настроек и кэшируются в экземпляре реестра; `register`
и `unregister` начинают новую версию. То, что не принадлежит одному каталогу,
общее для всего процесса: встроенный лексикон читается и строится один раз, а
разобранные поля каждого инструмента кэшируются по его `ToolDocument`, так что
реестр над уже знакомыми процессу инструментами — у хоста, который строит его на
каждый запрос, или в каталоге, где изменился один инструмент, — только
пересчитывает оценки. На ~700 инструментах первое построение занимает около
110 мс, повторное над знакомыми инструментами — около 20 мс, запрос — заметно
меньше миллисекунды.

**Ранжировщик хоста.** `ToolRegistry(retriever=...)` принимает `IToolRetriever`
(`contracts/tool_retrieval.py`): синхронный `rank(query, documents, limit)`,
возвращающий имена, лучшие первыми. Его ранжирование сливается с лексическим
через reciprocal rank fusion (`reciprocal_rank_fusion`, `k` =
`tool_retrieval_fusion_rank_constant`). Задуман он для эмбеддингов; сам core их
не поставляет.

### Как писать `search_hint`

Описание пишется для модели, по-английски; подсказка — для того, кто ищет.
Она должна быть у каждого инструмента хоста, как есть у собственных
инструментов ядра (`AskUser`, `ToolSearch` и инструменты памяти; `AskUser`
загружен всегда, но `ToolSearch` всё равно его ранжирует):

- **8–14 английских синонимов** действия и его объекта, не повторяя имени
  инструмента ("screenshot capture snap picture image page").
- **10–16 русских слов**: словарная форма **и** повелительное наклонение каждого
  глагола (открыть открой, напомнить напомни), существительные объектов и
  сленг и кальки, которые люди действительно пишут (скинуть скинь, глянуть
  глянь, коммит, пулреквест, напоминалка).
- **Избегайте общих слов**, которые совпадут и с чужими инструментами, —
  "запрос", "задача", "сервер" без уточнения уводят запросы к не тому
  инструменту.

## Отложенные группы инструментов

Отдавать все инструменты — лучшая поверхность, пока она помещается: на
нескольких моделях поверхность примерно из двухсот инструментов отвечала не хуже
любого способа искать инструменты по требованию. Перестаёт помещаться она двумя
способами, и оба — стены, а не склоны. Определения могут занять столько окна,
что разговору не останется места, а некоторые провайдеры отказывают в запросе
сразу, если инструментов больше фиксированного числа (встречаются 128 и 350).
Хост, подключивший большой MCP-сервер, упирается в одну из стен на первом же
запросе.

Поэтому цикл умеет откладывать целые **группы** инструментов: не класть их в
`tools`, называть одним блоком в системном промпте и загружать по запросу через
`ToolSearch`. Пока поверхность помещается, ничего из этого не происходит — если
только хост не попросил: группа, объявленная **ленивой** (`lazy`), откладывается
и тогда, потому что это семейство, которое прогону нужно редко.

### Группы

Инструмент попадает в группу по атрибуту класса `tool_group` (читается через
`getattr`, как `search_hint`) или по префиксу имени, который объявил хост:

```python
registry.declare_group("scheduling", "Timed and recurring jobs")
registry.declare_group(
    "github", "GitHub issues and pull requests", dynamic=True, prefix="Mcp_Github_"
)
registry.declare_group(
    "browser",
    "Drive a web browser",
    prefix="Browser",
    load="lazy",
    instructions="Ask the user before submitting a form.",
)
registry.register(ToolSearchTool(registry))
```

`ToolGroup(name, description, dynamic, prefix, load, instructions)` живёт в
`contracts/tool_registry.py`, у `IToolRegistry` появились `declare_group` и
`tool_groups`. `declare_group(name, description, *, dynamic=False, prefix=None,
load="auto", instructions="")` отклоняет режим загрузки вне `TOOL_GROUP_LOADS` и
правила длиннее `TOOL_GROUP_INSTRUCTIONS_MAX_CHARS` (8 000 символов, около двух
страниц); повторное объявление группы заменяет описание, режим и правила, и цикл
принимает решение заново на следующем запросе. Явный `tool_group` важнее префикса; из префиксов побеждает самый
длинный. Членство в группе не уходит на провод и не входит в дайджест
поверхности. **Динамическая** группа — та, состав которой не код хоста: прокси
MCP-сервера.

`undeclare_group(name)` забывает группу; забыть не объявленную — не ошибка.
Хост вызывает его, когда инструменты группы ушли насовсем — прокси MCP-сервера,
который оператор выключил или удалил: объявление переживает свои инструменты, и
оставленное займёт префикс сервера, добавленного позже под тем же именем. Ни
объявление, ни удаление группы не меняет поколение каталога реестра: группы не
влияют на результат поиска, а решение цикла об откладывании привязано к самим
объявленным группам.

### Режимы загрузки

`load` группы говорит, когда она объявляется:

| `load` | Откладывается |
|---|---|
| `eager` | никогда из-за размера; сдвинуть её может только жёсткий лимит провайдера на число инструментов |
| `auto` (по умолчанию) | по правилам ниже: динамические сразу, остальные — пока поверхность превышает предел |
| `lazy` | всегда, когда прогону допущен инструмент обнаружения, при любом размере |

`lazy` — для семейств инструментов, которые прогону нужны редко: дюжина
инструментов браузера, использованная в одной сессии из ста, стоит своих
определений на каждом запросе остальных девяноста девяти; отложенная, она стоит
одной строки каталога и одного вызова на загрузку. Прогон без инструмента
обнаружения считает `lazy` равным `auto`: единственным путём тогда был бы вызов
вслепую по точному имени, а он дороже определений. Группа, которую называет
только атрибут `tool_group` инструмента и которая не объявлена, — `auto`.

`eager` сильнее бюджета по токенам, правила динамических групп и запаса на
загруженные инструменты, но не самого `max_advertised_tools`: запрос сверх
лимита провайдера отклоняется целиком, и никакой режим этого не стоит. Поэтому
жадная группа откладывается, только пока поверхность и с отложенными всеми
остальными группами всё ещё превышает этот лимит, — самая большая первой.
Группа, ставшая жадной, выходит из нижней границы прежнего решения (см. ниже):
оператор попросил её по имени.

`QueryEngineConfig.tool_group_loads` — отображение «имя группы → режим» —
переопределяет объявления на один прогон; значение вне трёх отклоняется. Через
него хост передаёт настройки оператора и исключения отдельной сессии, не
переобъявляя группу, общую для всех сессий. Оно входит в ключ, по которому
принимается решение об откладывании.

### Когда группы откладываются

`tool_deferral_mode` по умолчанию `"auto"`, `"off"` выключает механизм. В
`auto` один раз за прогон — и заново, только если меняются каталог или группы
реестра, политика видимости хоста, профиль выполнения или объявленный набор
инструментов дочернего прогона, — цикл измеряет поверхность, которую иначе
отправил бы. Политика учитывается потому, что хост может включить инструменты
посреди прогона, заменив её и ничего не регистрируя; профиль — потому, что он
перекраивает ту же поверхность: решение, принятое под профилем плана, который
не допускал ни одного инструмента сервера, ничего не отложило и иначе осталось
бы в силе, когда профиль закончится, и сервер целиком оказался бы на
поверхности; пины, которые прогон добавляет за загруженные инструменты, не
учитываются, так что загрузка инструмента решение не пересматривает:

1. откладываются все **ленивые** группы, самые большие первыми, если допущен
   инструмент обнаружения;
2. откладываются все **динамические** группы, кроме жадных, самые большие
   первыми;
3. затем, пока поверхность превышает предел — определения больше
   `tool_definitions_ratio` окна или их число больше `max_advertised_tools` с
   запасом на `pinned_tool_max_count` загруженных инструментов, — остальные
   группы, самые большие первыми; жадные последними и только пока превышен сам
   лимит по числу.

Никогда не откладываются: обязательный пол (`forced_pinned`), явно закреплённые
инструменты, инструменты `always_load`, сам инструмент поиска и любой
инструмент вне групп. Хост, который хочет сделать инструмент откладываемым,
говорит об этом, помещая его в группу.

Измеряется та поверхность, которую прогон вправе вызывать: поверхность
политики, суженная до объявленного набора инструментов дочернего прогона
(`subagent_tool_allowlist`) так же, как её сужает диспетчер. Инструмент вне
объявления кандидатом не становится, так что дочернему прогону никогда не
показывают строку каталога для группы, которую он не может загрузить: группа,
ни один инструмент которой ему нельзя вызывать, не называется вовсе, а группа, из
которой ему доступен один инструмент, называется с ним одним.

Если инструмент обнаружения (роль `discovers_tools`) не зарегистрирован или не
допущен, вернуть отложенный инструмент можно только вызовом по точному имени,
поэтому группы откладываются лишь тогда, когда поверхность больше
`max_advertised_tools` — провайдер отклонил бы запрос целиком, — сначала
динамические; бюджет по токенам тогда не применяется. Каталог в этом случае
говорит вызывать по точному имени, а не указывает на поиск, которого у модели
нет.

Отложенные инструменты остаются **допущенными** политикой видимости — их просто
не объявляют. Модель, вызвавшая такой инструмент по точному имени, получает
результат (см. [ниже](#вызов-необъявленного-инструмента)).

Решение принимается один раз, а не на каждый запрос, потому что каталог, который
из него получается, стоит в голове кэшируемого промпта: пересчитываемый на
каждом запросе, он сдвигался бы при каждой смене ответа. Когда смена каталога
или политики заставляет принять его снова, действующее решение — его нижняя
граница: отложенная группа остаётся отложенной, пока в ней есть инструменты, и
добавить к ней может только динамическая группа, впервые допущенная этому
прогону, или превышенный теперь лимит. Другая сессия, включившая сервер, или
выключенный посторонний инструмент каталог не меняют.

### Каталог

Когда что-то отложено, в системном промпте после каталога навыков стоит один
блок `<system-reminder>`: фраза о том, что инструменты можно загрузить в любой
момент, и как — `ToolSearch(group="<name>")` для целой группы, `select:` и
точные имена для отдельных инструментов или описание, — фраза о том, что
отдельный инструмент лучше обходного пути через общий, и по строке на
отложенную группу — описание и **точные** имена инструментов, а для группы,
объявленной префиксом, у которой отложено больше
`tool_catalogue_max_listed_names` инструментов, — точный префикс и их число:

```text
- browser: Drive a web browser. Tools: BrowserClick, BrowserOpen
- scheduling: Timed and recurring jobs. Tools: IntentCreate, ScheduleCreate

Tools of connected servers:
- github: GitHub issues and pull requests. Tools: Mcp_Github_* (26 tools)
```

Собственные группы хоста идут первыми, а `dynamic`-группы — подключённые
серверы — после них, отдельной секцией. Когда всё шло одним списком по имени,
дюжина строк серверов стояла перед группами хоста, и модель, читающая сверху,
принимала их за весь каталог: вела браузер сервера или оболочку и так и не
загружала группу, сделанную для этой работы. Пробовали и фразу над группами
хоста, называющую эти обходные пути: под ней модели чаще загружали группы, но
задачу решали не лучше, так что её нет.

Точные имена важны: модель, которой приходится угадывать имя, ошибается в
регистре. Вторая фраза важнее, чем кажется: модель, не видящая инструмента,
тянется к ближайшему видимому (сервис через команду оболочки, две правки вместо
одной множественной), и обычно отложенный инструмент остаётся неиспользованным
именно так, а не из-за неудачного поиска. Блок строится из решения, каждая секция
в порядке имён, поэтому он побайтно одинаков на каждом запросе и после возобновления.
Когда ничего не отложено и ни у одной группы нет правил, блока нет, и промпт в
точности такой же, как без групп.

### Правила группы

Группа может нести `instructions` — правила работы с её инструментами: какой
браузер вести, о чём спросить до действия. Весят они столько, сколько весят:
группа на поверхности стоит своих правил в каждом запросе, поэтому при
откладывании они считаются вместе с определениями группы против
`tool_definitions_ratio`, и группа, одни правила которой уже превышают бюджет,
откладывается и даёт их один раз — в результате, который её загружает. Группа,
которую отложить нельзя — закреплённая или `eager`, — кладёт правила в каждый
запрос, что бы ни говорил бюджет, и потому их длина ограничена при объявлении
(`TOOL_GROUP_INSTRUCTIONS_MAX_CHARS`): правилам длиннее двух страниц место в
навыке, который модель загружает, когда он нужен. Даются они один раз за прогон
там, где инструменты группы впервые оказываются перед моделью, и никогда — для
группы, которой прогон не касается:

- **В каталоге** — для инструментов, которые есть с самого начала: группа,
  оставшаяся на поверхности, и отложенная группа, часть инструментов которой
  загружена к началу прогона (посев хоста или возобновлённый снапшот). Правила
  отложенной группы стоят под её строкой с отступом; правила группы на
  поверхности — после списка. Блок, в котором есть правила и ничего не
  отложено, идёт без шапки:

  ```text
  - browser: Drive a web browser. Tools: BrowserClick, BrowserOpen
    Rules for the browser tools:
    Ask the user before submitting a form.
  ```

  Каталог строится один раз за прогон и входит в кэшируемый префикс. Он
  строится заново в запросе после загрузки группы, правил которой в нём ещё
  нет: у этого запроса новый список инструментов, и он всё равно промахивается
  мимо кэша от самого начала промпта, — так правила попадают в каталог там же,
  и следующий прогон сессии, засеянный теми же инструментами, строит тот же
  каталог. Если отложить это до следующего прогона, системный промпт менялся
  на прогон позже списка инструментов, и сессия платила второй промах по
  всему контексту за одну загрузку. После компакции он пишется снова с правилами ровно тех групп,
  что на поверхности или ещё загружены, потому что результат, который их дал,
  теперь может быть в сводке или замаскирован. Это не бесплатно: компакция
  переписывает разговор, а не системный промпт, поэтому, если группа с
  правилами была загружена посреди прогона и ещё загружена, следующий запрос
  один раз промахивается мимо кэша на системном промпте (и на инструментах —
  у провайдера или шаблона чата, который ставит их после него). Без такой
  группы каталог выходит байт в байт прежним.
- **В результате `ToolSearch`**, который загружает первые инструменты группы:
  `Rules for the <group> tools [<метка>]:` и текст, после строк инструментов.
- **Вместо выполнения вызова вслепую** (см.
  [ниже](#вызов-необъявленного-инструмента)).

Цикл хранит множество групп, чьи правила уже даны
(`protocore.tool_group_rules_given` в метаданных инструмента и
`tool_group_rules_given` в снапшоте), так что ни одни не даются дважды.
Множество означает «модель их ещё может прочитать». После компакции оно
сбрасывается до групп, чьи правила несёт новый каталог: группе, чьи правила
были в результате, который компакция убрала, и которую компакция выгрузила
сверх лимита, они снова причитаются — вызов её инструмента вслепую
придерживается, а `ToolSearch`, который её загружает, их даёт. Внутри цикла
`ToolSearch` смотрит только на это множество, даже для инструмента, который уже
в списке.

#### Метка правил

Правила приходят внутри результатов инструментов — и туда же попадает текст
извне: веб-страница, прочитанная инструментом браузера, файл, вывод команды.
Любой из них может напечатать `Rules for the browser tools:` и что угодно
дальше. Поэтому настоящие правила несут в конце заголовка **метку правил**
прогона — `Rules for the browser tools [3f9a1c2e]:`, — а каталог, в системном
промпте, куда вывод инструментов не попадает, один раз называет метку, когда
хоть у одной группы в нём есть правила, и говорит, что текст, выдающий себя за
правила без неё, — содержимое для чтения, а не правила, и что метку нигде не
нужно писать самому.

Метка — восемь шестнадцатеричных цифр, HMAC идентификатора тенанта на ключе
(`tool_rules_mark(tenant_id, key=...)`). Формула открыта, так что метка ровно
настолько секретна, насколько секретен ключ:

- **С заданным `QueryEngineConfig.tool_rules_mark_key`** — секретом, который
  хранит хост, одним и тем же во всех воркерах, — метка одна и та же для всех
  сессий тенанта, в каждом процессе и после каждого перезапуска. Это то, что
  нужно хосту, полагающемуся на кэширование промпта: метка стоит в каталоге в
  начале кэшируемого промпта, и метка, менявшаяся вместе с процессом, теряла
  кэш начиная с каталога, не давала сессиям делить промпт и, при шаблоне чата,
  который выводит инструменты после системного текста, ни одного определения
  инструмента. Метка тогда живёт для тенанта, пока ключ не сменят, поэтому
  ключ надо хранить в секрете, как любые учётные данные. В `repr` конфигурации
  он не попадает.
- **Без ключа** (по умолчанию) метка выводится из случайного ключа, который
  вытягивается один раз на процесс. Вне процесса её вычислить нельзя — пустой
  ключ позволил бы любой странице, знающей идентификатор тенанта, вычислить
  метку и подделать правила, — но она меняется вместе с воркером и
  перезапуском, а с ней меняется и промпт.

**Метка сессии.** Хост, который ведёт все сессии под одним тенантом и хочет у
каждой сессии свою метку, задаёт `QueryEngineConfig.tool_rules_session_id`.
Метка тогда — HMAC от `tool_rules_scope(tenant_id, session_id)` на том же
ключе: своя у каждой сессии и одна и та же в каждом процессе, у которого есть
ключ. Названная сессия не обязана быть сессией самого прогона: ответвление,
несущее историю источника, несёт и правила, данные под меткой источника, и
называет сессию источника, чтобы сохранить её метку, а с ней и байты промпта.
При `None` областью служит идентификатор тенанта, и метка — метка тенанта, как
выше.

Снапшот несёт метку (`tool_group_rules_mark`), так что возобновлённый прогон
сохраняет метку, с которой даны правила в его истории, какой бы процесс его ни
подхватил и каким бы ни был ключ теперь. Цикл передаёт её как
`protocore.tool_group_rules_mark` только инструменту обнаружения — единственному,
который пишет правила, — так что никакой другой инструмент не может её
переслать или записать в лог.

Отдельное сообщение от среды выполнения для правил рассматривалось и
отвергнуто: ход пользователя между результатом инструмента и следующим ходом
ассистента — последовательность, которую некоторые шаблоны чата не принимают
(цикл избегает её и в других местах), а правила в ходе пользователя читаются
как слова оператора. Метка оставляет правила там, где они нужны, — рядом с
инструментами, к которым они относятся, — и делает подделку узнаваемой.
Прогон, у групп которого нет правил, метки в промпте не получает, и промпт
остаётся ровно прежним.

### `ToolSearch`

`protocore/tools/tool_search.py` поставляет инструмент обнаружения:
`ToolSearchTool(registry)` с именем `ToolSearch`, ролью `discovers_tools` в
собственном `tool_roles`, флагом `always_load` и диспетчеризуемый по одному
вызову (не `is_concurrent_safe`): то, что должен дать один вызов, зависит от
того, что дали предыдущие вызовы того же сообщения, и при параллельном запуске
две загрузки одной группы в одном сообщении обе несли её правила; при
последовательном цикл вкладывает каждый результат до того, как следующий вызов
получает список групп, чьи правила уже даны, а локальное ранжирование ничего не
стоит выполнять по очереди. Цикл объявляет его **только пока ему есть что искать**: отложена
группа, или — при включённом `tool_retrieval_top_k` — допущенные инструменты,
которые отсечение по сообщению не пустило на поверхность; поиск находит и
загружает их как любые другие. Допущенные — в том смысле, в каком их допускает
диспетчеризация: инструмент вне объявленного набора дочернего прогона — не
повод оставлять поиск, который никогда не сможет его загрузить. Когда весь каталог на поверхности, его нет в
списке, и промпт ровно такой, каким был бы без него: модель, которой предложили
ненужный поиск, тратит на него ходы.

- `query` свободным текстом возвращает до `tool_search_max_results` совпадений,
  лучшее первым, по строке на каждое — `Name(param1, param2*) — первая фраза`,
  обязательные параметры со звёздочкой, — и загружает первые
  `tool_search_autoload_count`. Модель, которая ищет, почти всегда находит нужный
  инструмент среди первых трёх.
- `select:Name1,Name2` загружает ровно эти инструменты (имя в другом регистре
  тоже принимается). На неизвестное имя приходят ближайшие допущенные имена.
  Имена можно передать и отдельным аргументом `select` — списком или строкой
  через запятую: модели сами тянутся к такому написанию, и отказ стоит им
  лишнего хода. Имена важнее описания, переданного рядом.
- `group` загружает все допущенные инструменты одной группы, названной точно
  (имя в другом регистре тоже принимается); `select` принимает также элементы
  `group:<name>` рядом с именами инструментов. На неизвестную группу приходит
  список групп, доступных прогону. Результат перечисляет инструменты группы
  по строке, как при любой загрузке. Инструменты, загруженные целой группой, —
  **одна запись** под `pinned_tool_max_count` и выгружаются вместе: модель,
  попросившая группу, не заметит, что вытеснение оставило от неё половину.
  Группа загружается целиком, только пока вся она помещается рядом с
  инструментами, уже стоящими в списке, — под `max_advertised_tools` и под
  бюджетом определений инструментов (`group_load_overflow`): загруженная сверх
  любого из них, она была бы урезана на следующем запросе или отклонена вместе
  с ним, а большая группа, загруженная целиком, сводит на нет то, что сберегло
  её откладывание. «Уже в списке» — это то, что понесёт следующий запрос:
  группы, взятые раньше в том же вызове, и инструменты, загруженные
  предыдущими вызовами того же сообщения модели
  (`TOOLS_LOADED_THIS_STEP_METADATA_KEY`), а не только объявленные, так что
  две группы, каждая из которых помещается сама по себе, но не вместе, не
  объявляются загруженными обе. Группа, которая не поместится, не загружается; результат
  называет стену, в которую она упёрлась, и перечисляет её инструменты (до
  `tool_search_max_results`), чтобы модель загрузила нужные через `select:`.
- Первые инструменты группы с правилами, загруженные вызовом, приносят правила,
  один раз (см. [Правила группы](#правила-группы)).
- Первые строки результата говорят, какие инструменты теперь загружены и
  доступны, и отдельно — какие из запрошенных или найденных **уже были в списке
  инструментов**. Что объявил вызвавший запрос, цикл сообщает инструменту
  (`ADVERTISED_TOOLS_METADATA_KEY`; ставится после слияния операторского
  конверта, так что подделать его нельзя). «Loaded» про инструмент, который у
  модели и так был, вводит в заблуждение: модель, которую попросили
  воспользоваться навыком, искала его, получила «Loaded: WebSearch», решила, что
  навык загружен, и так его и не открыла. Об этом говорит и описание: инструмент
  загружает только инструменты, а навык — не инструмент.
- Живая политика видимости читается из `ToolContext.metadata`
  (`TOOL_VISIBILITY_POLICY_METADATA_KEY`, `protocore.tool_visibility_policy`),
  рядом — объявленный набор инструментов дочернего прогона
  (`TOOL_ALLOWLIST_METADATA_KEY`), поэтому поиск никогда не показывает, не
  предлагает и не загружает инструмент, который отклонит гейт диспетчеризации,
  а заблокированное имя никогда не всплывает как «похожее». Диспетчер
  присваивает оба ключа при каждом вызове, а не ставит их, только если их нет,
  так что значение, уже лежавшее в метаданных, не подменяет то, что применяет
  гейт. Без политики в метаданных поиск не допускает ничего.

Инструмент только ранжирует и сообщает. Что он загрузил, он называет под
`TOOLS_LOADED_METADATA_KEY` в метаданных результата — группы, загруженные
целиком, под `TOOL_GROUPS_LOADED_METADATA_KEY`, группы, чьи правила он дал, под
`TOOL_GROUP_RULES_METADATA_KEY`, — а загружает цикл — он
владеет поверхностью, — веря этому ключу только от инструмента с ролью
`discovers_tools` и только для имён, которые допускает политика (и объявленный
набор инструментов дочернего прогона). Настройки читаются из констант прогона в
`ToolContext.run_state.rc`; движок, собранный без состояния прогона от хоста,
кладёт туда собственные константы.

### Порядок обнаружения и кэш промпта

Загруженные инструменты **дописываются** в конец объявленного списка в порядке
обнаружения и там остаются. Базовая поверхность остаётся отсортированной по
имени и не двигается, когда что-то загружается, а загруженный инструмент не
двигается, когда загружается следующий, поэтому провайдер с кэшем по префиксу
перечитывает только хвост: одна загруженная схема стоит порядка пары тысяч
некэшированных токенов, а не всего префикса. Найденный инструмент, который уже
на поверхности, повторно не загружается.

Прогон хранит загруженные инструменты в порядке обнаружения вместе со временем
последнего использования (`ContextManager.discover_tool`, `note_tool_used`).
`pinned_tool_max_count` ограничивает их число, но выгружает давно не
использованные только там, где префикс промпта и так начинается заново: после
компакции, на границе хода (`rearm`) и в начале прогона. Выгрузка посреди
прогона выдернула бы схему из-под модели, которая, возможно, как раз собирается
её вызвать, и стоила бы кэшу ровно того, что ограничение должно экономить.
Единственное исключение — лимит провайдера: если базовая поверхность вместе с
загруженными инструментами превысит `max_advertised_tools` — база выросла под
загруженным хвостом, который прежде помещался, — давно не использованные
загруженные записи не попадают в этот запрос (оставаясь загруженными). Запись —
инструмент или группа, загруженная целиком, как и при вытеснении: группа
выпадает целиком и никогда не урезается под оставшееся место, так что сказанное
модели о ней остаётся верным для списка перед ней; меньшая и более старая запись
может занять её место.

Загруженные инструменты и отложенные группы переносятся в снапшоте
(`discovered_tools`, `deferred_tool_groups`), и возобновлённый прогон сохраняет
решение, а не измеряет заново, — как нижнюю границу: динамическая группа,
которой нет в снапшоте (сервер, подключённый позже), всё равно откладывается, и
лимиты по-прежнему применяются поверх. Хост, который хочет, чтобы следующий
прогон сессии начинался с теми же инструментами, передаёт список в
`QueryEngineConfig.discovered_tools`: голые имена или строки, которые пишет
`ContextManager.discovered_tool_state()`. Строки возвращают загруженный хвост
в том порядке, в каком он загружался, и инструмент из целой группы остаётся с
ней одной записью; голые имена встают первыми, а `loaded_tool_groups` — после
них, так что прогон, загрузивший группу и потом ещё один инструмент, начал бы
следующий с этими двумя наоборот — промах по всему промпту ни за что.
`ContextManager.called_discovered_tool_names()` — та часть загруженных, которую
прогон действительно вызывал, для хоста, который предпочтёт переносить меньше,
чем сохранять префикс: поиск загружает несколько лучших совпадений, нужны они
модели или нет.
Инструмент из переданного списка считается вызванным. Каждая строка снапшота
несёт `called`; строка без него считается вызванной. Строка инструмента,
загруженного в составе целой группы, несёт ещё и `group`.

Загруженный инструмент — переданный хостом, восстановленный из снапшота или
загруженный по ходу прогона — допускается ровно так же, как любой другой.
Движок добавляет имена загруженных в `pinned`, чтобы диспетчер допускал их при
белом списке `visible`, но только те имена, которые политика хоста допускает
сама: `pinned` проходит мимо `visible`, и загруженное имя вне белого списка
иначе стало бы вызываемым просто потому, что было загружено. Проверка делается
на каждом запросе: инструмент, который оператор убрал из белого списка между
прогонами, не возвращается через переданный список, а убранный посреди прогона
со следующего запроса не объявляется и не вызывается; объявленный набор
инструментов дочернего прогона применяется к загруженным так же. Список
загруженных при этом имя сохраняет — оно вернётся, если политика снова его
допустит, — и переданный хостом список для следующего прогона проверяется так
же.

Группу целиком переносят через `QueryEngineConfig.loaded_tool_groups`: каждая
названная там группа загружается так же, как её загрузил бы
`ToolSearch(group=...)`, — только те инструменты, которые прогону можно
вызывать, одной записью под `pinned_tool_max_count`, новее инструментов,
переданных по именам, с правилами в каталоге и событием `tool_group_loaded` с
`via` `seed`. Если передать инструменты большой группы по одному, каждый станет
отдельной записью, и ограничение вытеснит остальное. `ContextManager.loaded_tool_group_names()`
— группы, которые прогон держит целиком. Инструменты переданной группы не
считаются вызванными, так что хост, переносящий только те группы, инструмент
которых прогон вызывал, отпускает неиспользованную группу через один прогон.

### Вызов необъявленного инструмента

Диспетчеризация проверяет политику видимости, а не объявленный список, поэтому
вызов отложенного инструмента по точному имени выполняется, как и раньше.
Теперь он ещё и **загружается**, так что со следующего запроса модель видит его
схему, а цикл эмитирует `tool_unadvertised_call`.

Исключение — инструмент, у группы которого есть правила, ещё не данные прогону.
Такой вызов написан без схемы и без правил и действовал бы наугад ровно там,
где правила должны всё решить. Поэтому он **не выполняется**: загружается
**вся его группа**, как её загрузил бы `ToolSearch(group=...)` (допущенные
инструменты, одна запись под лимитом), правила группы отмечаются данными (сам
вызов не считается использованием инструмента — он не выполнялся), а на
вызов приходит ответ — не ошибка, ведь ничего не сломалось — с правилами,
именами остальных теперь доступных инструментов группы и строкой вызванного
инструмента: «BrowserOpen is loaded now; call it again. It takes:
BrowserOpen(url*) — …». Следующий вызов выполняется. Вся группа — потому что
работа, начатая одним её инструментом, обычно требует следующего, и модель, у
которой был загружен только вызванный, обходилась без остальных; строка —
потому что повтор по памяти повторял неверные аргументы. Когда вся группа не
поместится в список инструментов (те же две стены, что у
`ToolSearch(group=...)`), загружается только вызванный инструмент — сам по себе,
не как группа, — а ответ говорит, сколько их ещё и как загрузить нужные: один
вызов вслепую — не запрос большой группы. Второй вызов вслепую
той же группы в том же сообщении тоже ждёт и отсылает к первому ответу, а не
повторяет правила. `tool_unadvertised_call` для такого вызова несёт `executed: false`
и, в отличие от выполненного вызова, приходит до его `tool_result`, чтобы хост,
который замеряет вызовы или считает их использованием, знал: результат отвечает
на вызов, который не выполнялся.
Модели достаточно часто берут точное имя из каталога и вызывают его без
загрузки, так что отказ в вызове стоил бы им заметно; это же стоит один шаг и
только для групп с правилами.

На имя, которое вовсе не
зарегистрировано, приходит `unknown tool: 'X'. Did you mean: A, B, C?` — до трёх
зарегистрированных имён, допущенных политикой, без учёта регистра.

Такой вызов написан без схемы, и его аргументы — догадка. Если он падает на них,
ошибка кончается строкой инструмента в форме `ToolSearch` —
`It takes: Name(param1*, param2) — первая фраза`, — и повторная попытка верна
сразу, а не после ещё одной ошибки. «Падает на аргументах» понимается широко,
потому что инструмент, сам проверяющий аргументы, сообщает о плохом аргументе
результатом с ошибкой, а не исключением: ошибка валидации диспетчера,
исключение `TypeError`, `ValueError` (включая `ValidationError` pydantic) или
`KeyError`, либо результат с ошибкой, который инструмент считает сбоем.
Инструмент, который был в списке, этой строки не получает: его схема и так
перед моделью. Не получает её и инструмент, который отклоняет политика или
объявленный набор дочернего прогона: проверки аргументов идут до гейта, а
отклонённый инструмент никогда не «загружен».

### Телеметрия

- `tool_group_loaded` — `{group, via, tools}`, по разу на загрузку, которая
  принесла новые инструменты группы: `via` — `search` или `select` (запрос или
  имена в `ToolSearch`), `group` (загрузка целой группы), `direct_call` (вызов
  вслепую) или `seed` (инструменты, с которыми хост начал прогон; объявляются
  рядом с первым объявлением поверхности). `tools` — добавленные этой загрузкой
  инструменты группы.
- `tool_surface_advertised` несёт `tool_groups`: каждую группу с инструментом на
  предполагаемой поверхности, `{name, load, state}`, где `load` — режим, с
  которым работает прогон, а `state` — `advertised`, `deferred` (отложена,
  ничего не загружено) или `loaded` (отложена, часть инструментов загружена в
  этот запрос). В `tool_deferral_reasons` появилось `lazy`.

### Лавина вызовов

`max_tool_calls_per_turn` (по умолчанию 24) ограничивает число вызовов
инструментов из одного сообщения модели. Этого хватает на настоящий веер
вызовов — скажем, прочитать пару десятков файлов разом, — а одно сообщение-лавина
остаётся далеко от мягких пределов вызовов на прогон. Вызовы сверх него получают по ошибке и
не выполняются, так что у каждого вызова остаётся результат и транскрипт
корректен. Они не считаются сбоем инструмента — иначе тысяча отклонённых копий
одного поиска сработала бы на нём предохранителем. Больше тысячи параллельных
вызовов в одном сообщении на практике встречалось.

### Почему не стоит отсекать по сообщению

`tool_retrieval_top_k` по-прежнему отсекает поверхность до инструментов, лучше
всего подходящих к последнему сообщению пользователя, но по умолчанию выключен и
не рекомендуется. Он переранжирует поверхность на каждом сообщении
пользователя, так что список инструментов — а с ним и кэшированный префикс у
провайдера — меняется вместе с сообщением. Он ранжирует слова пользователя, а
не модели: русское сообщение против английских описаний примерно в половине
случаев теряет нужный инструмент, а модель, не видящая нужного инструмента,
склонна выдумать ему имя. Модель, ищущая через `ToolSearch`, пишет запрос сама,
обычно по-английски, и находит инструмент. Вместо отсечения откладывайте
группы.

### Схемы текстом

Отдавать загруженный инструмент текстом в результате и вызывать через общий
`CallTool(name, arguments)` значило бы держать список инструментов неизменным.
Это не реализовано. В сравнении с загрузкой такой способ отвечал хуже на
слабых моделях, которые заполняли аргументы без ограниченного декодирования
провайдера, а экономия кэша у провайдера с кэшем по префиксу — те несколько
тысяч токенов, которые и так стоит дописывание. Сделать это правильно значило бы
ещё и переписывать каждый `CallTool` в настоящий вызов до того, как его увидят
гейт разрешений, хуки, предохранитель и предусловия, и проверять аргументы по
схеме, которую провайдер больше не применяет.

## Предусловия инструментов

Предусловия обеспечивают **порядок** инструментов: инструмент, требующий
предшествующего наблюдения, маскируется, пока его предусловие не удовлетворено,
так что модель не может, например, изменить запись до прочтения управляющей
политики.

Существуют две системы; они никогда не взаимодействуют:

- **Runtime DAG** — `runtime/tool_preconditions.py` (`check_preconditions`,
  `resolve_precondition`, `record_satisfaction`, `compute_masked_tools`,
  `derive_satisfied_from_messages`). `preconditions` инструмента
  читаются из его `ToolDefinition`; удовлетворённый набор перевоспроизводится
  из сообщений самого прогона, поэтому он переживает снапшот/возобновление,
  нигде не сохраняясь. Этот
  слой потребляется в пути диспетчеризации (шаг 4 выше) и гейтится
  `LoopConstants.tool_preconditions_enabled` (по умолчанию `False`). Он
  **блокирует** инструмент, который модель уже выбрала.
- **Run-level forcer** — `runtime/run_tool_preconditions.py` плюс
  `QueryEngineConfig.tool_preconditions`. Упорядоченный кортеж инструментов,
  которые этот запуск **должен** вызвать, прежде чем агент свободен отвечать;
  пока запись outstanding, цикл ставит `LLMRequest.extra['forced_tool_choice']`.
  Пустой кортеж (значение по умолчанию) — no-op. Это **принуждает** инструмент,
  который модель не выбирала.

См. раздел [Tool preconditions](architecture.md#инвентаризация-технологий)
о механизме предусловий.

## Что объявляет инструмент: роли и то, чем является его результат

**Роли, а не имена.** Рантайм спрашивает, что вызов ДЕЛАЕТ, а не как он
называется. Это сказано в `contracts/tool_roles.py`: `ToolRole` — способность
(`reads_path`, `writes_path`, `appends_path`, `edits_path`, `finalizes_path`,
`searches_workspace`, `runs_shell`, `fetches_url`, `delegates_work`,
`records_plan`, `discovers_tools`, `asks_user`, `never_delegated`), а
`ToolRoleMap` — приходящая как `QueryEngineConfig.tool_roles` декларация хоста
о том, какие из ЕГО имён какие роли несут. Та же карта несёт и написания
аргументов (`ToolArgumentSlot`): в каком ключе лежит команда шелла, в каком —
тело записи, в каком — ответ терминального инструмента. Рантайм читает сырые
аргументы до того, как какая-либо входная модель разрешит алиасы, поэтому ему
надо это сказать, а не угадывать.

Каждое сравнение имени инструмента со строкой, написанной внутри ядра,
допускало, что всякая установка называет инструменты так же, как первая. Хост,
назвавший свой шелл-инструмент иначе, терял deny-паттерны шелла, его записи
больших файлов переставали сходиться, и нигде об этом не говорилось —
сравнение просто никогда не совпадало. Теперь роль, которой карта не упоминает,
— это способность, которой у установки нет, и функция, которой она нужна,
говорит об этом предупреждением, а не становится тихо инертной.

Та же карта ограничивает делегированный прогон:
`runtime/child_capabilities.py::narrow_child_capabilities` вычисляет, что
позволено ребёнку, из его родителя и его `SubagentDef`, только сужая.
Применяется дважды — когда разрешается каталог ребёнка и на каждом его вызове —
потому что каталог не даёт показать ребёнку то, чего ему нельзя, а гейт не даёт
получить то, чего ему не показывали.

**Одно значение, три адресата.** `ToolResult.content` — каноническое значение,
полное, каким бы большим оно ни было. Проекции стоят рядом: `model_projection`
— то, что транскрипт несёт вместо него (первая страница длинного листинга,
`wrote 4.2 MB to <path>` для байтов, которые модели незачем перечитывать);
`ui_payload` едет на событии результата и в транскрипт не попадает, поэтому
целая отрисованная таблица не стоит токенов и не может изменить решение модели;
`canonical_ref` называет блоб, из которого значение можно достать целиком, — а
когда инструмент не называет ничего, компакция сохраняет значение сама в тот
момент, когда ей впервые нужно место, и заполняет это поле в блоке, который
переписывает. Инструмент, не назвавший проекции, говорит, что значение
достаточно мало, чтобы быть собственной проекцией: обычный случай, и он ничего
не стоит. Единственное исключение — хук `post_tool_use`, который переписывает
вывод: тогда значением становится текст хука, а оригинал отбрасывается вместе с
`canonical_ref` и `ui_payload`, которых хук не видел (см.
[полезную нагрузку хука](#полезная-нагрузка-post_tool_use)).

**Внешний текст — за оградой.** Инструмент, чьи результаты несут текст
извне прогона — загруженную страницу, результат поиска, ответ удалённого
сервера, — задаёт `output_trust = "untrusted"` (атрибут класса или экземпляра;
для декорированного — `@tool(..., output_trust="untrusted")`) или помечает
отдельный результат ключом `TOOL_OUTPUT_UNTRUSTED_METADATA_KEY` в его
метаданных. Диспетчер ставит этот ключ на каждый результат такого инструмента,
и там, где результат входит в прогон, после обрезки по пределу результата,
ядро оборачивает его текст в ограду из шаблона промпта
`untrusted_tool_output`: открывающий тег с именем инструмента, строка о том,
что это данные, а не инструкции, сам текст и закрывающий тег. Id тега — начало
SHA-256 от текста, поэтому текст не может заранее написать собственный
закрывающий тег и заговорить за оградой, а один и тот же текст на каждом
запросе огораживается одинаково, и кэш промпта не страдает. Обрезка оставляет
место для ограды, так что закрывающий тег она не срезает никогда.
`canonical_content` хранит собственный текст инструмента; событие результата
несёт огороженный текст транскрипта и ключ — так же, как несёт указатель
обрезанного результата. Ничего не распознаётся и не отклоняется: хост, который
ищет внедрённые инструкции, делает это в своём инструменте или в хуке
`post_tool_use`, который срабатывает раньше. Инструмент, который ничего не
сказал, считается доверенным, и его результаты не трогаются
(`runtime/untrusted_output.py`).

**Запись до вызова.** Каждый диспетчеризуемый вызов коммитит `IntentRecord`
(`runtime/intent.py`) до того, как инструмент тронут, с зарезервированными id
результата и явным жизненным циклом — `RESERVED`, `PENDING_APPROVAL`,
`DISPATCHED`, `PAUSED_ASK_USER`, `SETTLED`. Именно это позволяет поднятому
прогону различить вызов, который не начинался, вызов, исход которого честно
неизвестен, и вызов, ждущий ответа. Гадание стоит корректности в худшую
сторону: сообщить о прерванном вызове как о неудачном — пригласить модель его
повторить, а повтор вызова с побочным эффектом применяет этот эффект дважды.

## Расширение поверхности инструментов

- **Добавить инструмент:** реализуйте ABC `Tool` (`contracts/tools.py`) или
  используйте `@tool`; зарегистрируйте получившийся `ToolDefinition` в
  `IToolRegistry`.
- **Управлять видимостью:** задайте `visible` / `blocked` / `pinned` на
  `ToolVisibilityPolicy`.
- **Добавить проверку безопасности:** реализуйте `IToolSafetyPolicy` и
  передайте её в `QueryEngine(tool_safety_policies=...)`, после
  `ShellSafetyPolicyAdapter`, если прогон должен сохранить список запретов для
  оболочки; гейт вокруг них движок строит сам.
- **Объявить, что он делает:** добавьте роли (`ToolRole`) и слоты аргументов
  инструмента в `ToolRoleMap`, которую вы передаёте как
  `QueryEngineConfig.tool_roles`. Инструмент, которого карта не описывает,
  по-прежнему работает; он теряет каждое поведение, зависящее от знания, какого
  рода это вызов.
- **Гейтировать по наблюдённому состоянию:** правило вида «шаблон аргументов
  плюс уже наблюдённое в прогоне» — это вычислитель **хоста**, привязанный на шве
  жизненного цикла, а не механизм ядра. Двух систем предусловий ядра — DAG и
  run-level forcer выше — этим не заменить.

См. [`extending.md`](extending.md) для более широкого руководства «выберите свой
шов» и правила границ импорта.
