# Тестирование ядра

Как тестировать, линтить и проверять типы чистого ядра (`protocore`). Все команды
предполагают наличие [`uv`](https://docs.astral.sh/uv/) и запускаются из корня
репозитория.

## Подготовка

Установите пакет вместе с его зависимостями для разработки (pytest,
pytest-asyncio, pytest-cov, pytest-xdist, ruff, mypy, bandit):

```bash
uv sync --extra dev
```

Хосту, которому нужно только прогнать conformance-наборы против собственных
адаптеров, ставится куда меньше — см.
[Conformance-наборы для хоста](#conformance-наборы-для-хоста).

## Четыре гейта

Ядро верифицируется четырьмя независимыми гейтами. Запустите все четыре перед
тем, как предлагать изменение; CI выполняет те же самые команды.

```bash
uv run pytest .              # tests (+ coverage)
uv run ruff check .          # lint + import sorting
uv run mypy --strict         # static type-check
uv run bandit -r protocore -q -c pyproject.toml   # security scan
```

Примечания:

- **Тесты** — `pytest` обнаруживает их в `tests/` (настроено через
  `testpaths = ["tests"]` в `pyproject.toml`). Указано `asyncio_mode = "auto"`,
  поэтому `async def test_*` выполняется без отдельного маркера
  `@pytest.mark.asyncio` для каждого теста. Установлен `pytest-xdist`, поэтому
  `-n 8 --dist loadscope` гоняет набор параллельно; `--dist loadscope` держит
  тесты одного модуля на одном воркере, а `--dist load` — нет.
- **Линт** — `ruff` настроен с `line-length = 120`,
  `target-version = "py312"` и наборами правил `E,F,W,I,B,UP,RUF`.
- **Проверка типов** — запускайте `mypy` **без аргумента-пути**. Путь в командной
  строке заменяет список `files`, настроенный в `pyproject.toml`, и молча
  выбрасывает дерево тестов: проверка проходит, проверив меньше, чем должна.
- **Сканирование безопасности** — `bandit` по пакету, с конфигурацией из
  `pyproject.toml`. Никогда не пайпите гейт в `tail` или `head`: пайплайн
  сообщает статус *последней* команды, так что падающий гейт читается как
  успешный.

## Структура тестов

Тесты лежат в **корне репозитория, в `tests/`**, *а не* внутри пакета
`protocore`. Пакет не поставляет собственных файлов `test_*.py` — рантайм-код и
тестовый код физически разделены.

```
tests/
  conftest.py                      # shared fixtures (e.g. tenant_id)
  test_core_import_boundary.py     # import-boundary guard (see below)
  test_constructible.py
  test_runtime_constants_sse.py
  unit/
    contracts/                     # contract types + protocol shape tests
    runtime/                       # loop, dispatch, context, resilience, ...
    tools/                         # @tool decorator, ask-user, memory
    prompts/
    test_*.py                      # token counting, chain parser, JSON utils, ...
```

Набор быстрый и использует минимум моков: у ядра **нет зависимостей от внешних
сервисов** (нет базы данных, нет HTTP, нет Kubernetes — они скрыты за
контрактами, которые реализует хост), поэтому для запуска тестов ничего
поднимать не нужно.

## Guard-тест границы импорта

`tests/test_core_import_boundary.py` обеспечивает соблюдение центрального
архитектурного инварианта: **ядро никогда не импортирует вверх.** Он
разбирает через AST каждый файл `.py` в дереве пакета `protocore` и падает, если
какой-либо импорт верхнего уровня называет пакет, стоящий над ядром.

Правило — это пространство имён, а не список. Всё, что ядру позволено
импортировать у самого себя, лежит в единственном пакете `protocore`; хост
кладёт свои адаптеры, сервисный слой и фронтенды в соседние дистрибутивы,
чьи имена импорта начинаются с `protocore_`. Названная форма, а не перечень
сегодняшних соседей, ловит новый пакет в день его появления.

Иными словами, импорт любого модуля `protocore.*` обязан подтягивать **ноль**
символов из слоёв выше. Обращённые наружу возможности — это
`Protocol`-ы, которые ядро определяет, а хост реализует (см.
[`contracts.md`](contracts.md)); поведение добавляется через контракты, адаптеры
или `LoopConstants`, но никогда через импорт вверх (см.
[`extending.md`](extending.md)). Нарушение немедленно валит CI и сообщает по
каждому нарушителю `file: imports 'package'`.

## Conformance-наборы для хоста

Ядро объявляет свои зависимости как `Protocol`-ы и не видит объектов, которые им
удовлетворяют, пока прогон их не вызовет. `protocore.conformance` переносит этот
момент раньше: хост импортирует набор для контракта, привязывает его к
собственному адаптеру фикстурой-фабрикой и узнаёт в собственном прогоне тестов —
а не посреди хода агента, — что адаптер имеет ту форму, которую вызовет ядро.

```bash
pip install "protocore[testing]"     # наборам нужен тест-раннер и ничего больше
```

```python
from protocore.conformance import LLMProviderConformance

class TestOurProvider(LLMProviderConformance):
    @pytest.fixture
    def subject_factory(self):
        return lambda: OurProvider(...)
```

Параметром служит фабрика, а не экземпляр: набору может понадобиться больше
одного субъекта, а сборка каждого внутри теста не даёт состоянию одного случая
протечь в следующий. Проверяет набор сознательно структуру — наличие,
асинхронность и имена параметров, которые ядро передаёт по имени, — потому что
поведение проверяет собственный набор хоста, а ядро, утверждающее его, диктовало
бы семантику хранения, знать которую ему не положено.

Два набора добавляют поведенческие случаи, потому что обещание их контракта
нельзя прочитать из сигнатуры: `RequestManifestSinkConformance` (передача должна
возвращаться быстро) и `ToolOutcomeStoreConformance` (побеждает первый
записанный исход, поздний старт никогда не отменяет завершённый вызов, записи
разделены по прогону и тенанту, `discard` забывает только то, что назвали). Их
случаи держатся собственных run id, поэтому проходят и на хранилище, общем для
всех случаев.

`SUITES` — все наборы, которые публикует пакет, по одному на контракт, и
собственный тестовый модуль пакета падает, если контракт объявлен без набора, —
так что каталог не может отстать от `contracts/`.

Набор, который хост импортировал, но ни к чему не привязал, **скипается**: то
есть каталог conformance может пройти, ничего не утверждая. `bound_suites` — то,
чем хост отличает одно от другого: наведите её на собственный conformance-модуль
и сравните результат с контрактами, которые он реализует, — тогда забытая
привязка станет падением, а не тихим скипом.

## Позиция по покрытию

Покрытие собирается через `pytest-cov` по `source = ["protocore"]` с
`branch = true` (см. `[tool.coverage.run]` / `[tool.coverage.report]` в
`pyproject.toml`; файлы `__init__.py` исключаются, а тела Protocol-заглушек и
`overload` исключаются из знаменателя).

У ядра **строгий минимальный порог покрытия** — большинство новых возможностей
поставляются выключенными по умолчанию, поэтому их *включённые* пути
прорабатываются юнит-тестами, а не живым прогоном, и порог защищает от тихой
поставки непротестированных веток. CI обеспечивает его, запуская набор с
`--cov-fail-under=90`; изменение, опускающее покрытие ниже 90%, валит
пайплайн.

## Что запускать перед изменением

Запустите все четыре гейта локально перед тем, как предлагать изменение, — это
ровно то, что выполняет CI:

```bash
uv sync --extra dev          # однократно, чтобы установить инструментарий dev
uv run pytest .              # tests + coverage (должно проходить порог)
uv run ruff check .          # lint + import sorting
uv run mypy --strict         # строгая статическая проверка типов
uv run bandit -r protocore -q -c pyproject.toml
```

Guard-тест границы импорта (выше) выполняется в рамках `pytest`, поэтому обратный
импорт в соседний пакет немедленно валит прогон тестов.
